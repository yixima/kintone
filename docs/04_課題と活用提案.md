# データ活用に向けた課題と提案

`docs/03_データプロファイル.md` の実測値を踏まえた整理。

## A. データを使う前に把握しておくべき制約

### A-1. 営業管理(105) は「営業履歴」ではなく「見込み客リスト」
42 万件という数字に対し、実際の商談内容（連絡内容）が入っているのは 2026 年分で 1.3%、
営業フェーズが設定されているのも 2024 年以降で 20.3% にとどまる。
大半は「企画 × 顧客名」の当たりリストで、SNS アカウント名が顧客名欄に連結されている
（例: `千本 木晴　haru sembongi　sbg.haru　some/to　someto___`）。

→ **フェーズ分析・ファネル分析の母数として 42 万件をそのまま使うと実態を大きく誤る。**
　 分析するなら「営業フェーズが設定されているレコード」に限定する必要がある。

### A-2. 営業管理と契約管理が顧客IDで繋がっていない
営業管理の 2026 年分で顧客IDが入っているのは 107 件（0.4%）。
一方、契約管理の顧客ID は 3,914 名すべてが顧客マスタと一致している（不一致 36 件のみ）。

→ **「どの営業リストから受注に至ったか」を ID で追跡できない。**
　 現状は顧客名の文字列マッチに頼るしかなく、名寄せ精度が課題になる。

### A-3. 営業管理の「受注」件数と契約件数が桁違い
2024 年以降で営業管理のフェーズ「受注」は 10,898 件だが、同期間の契約管理の契約は 718 件。
同一顧客・同一企画のレコードが重複登録されている（10,339 組・延べ 40,492 件）ことが主因と思われる。

→ 受注率を計算する場合、営業管理側の件数は必ず重複排除してから使うこと。

### A-4. 請求・入金は 2019 年で止まっている
契約 42.1 億円に対し、請求管理に記録があるのは契約番号ベースで 7.5%。
**kintone 単体では売上 → 請求 → 回収の突合ができない。**
現在の請求業務がどこで行われているか（会計ソフト／Excel 等）を確認したうえで、
kintone に戻すか、外部システムとの連携を設計するかの判断が必要。

### A-5. フィールドの目的外利用・未使用
| アプリ | フィールド | 状況 |
| --- | --- | --- |
| 契約管理(94) | `情報１`〜`情報４` | 7,204 件すべて空（完全未使用） |
| 契約管理(94) | `営業区分` | 全件空 |
| 契約管理(94) | `部門１` `部門２` `部門３` | **担当者の「入社日」「誕生日」「部署」が入っている**（930 件）。部門情報ではない |
| 契約管理(94) | `支払条件` | 7 件のみ。値も「特別価格」等のメモ書きで条件になっていない |
| プロジェクトマスタ(91) | `受注目標` `件数目標` | 253 件すべて空（目標管理が未運用） |
| プロジェクトマスタ(91) | 実施／納品日程 | 253 件中 243 件が空 |

→ 目的外利用されているフィールドを機械的に集計すると誤った結果になる。

### A-6. マスタ整合性の欠落
- プロジェクトIDがプロジェクトマスタに存在しない契約: **257 件**
- パッケージIDがパッケージマスタに存在しない契約: **229 件**
- 契約番号の重複: **236 件**（同一顧客が同一企画の同一パッケージを複数契約したケースと、
  単純な二重登録が混在している可能性）
- 契約日が空: 535 件（金額計 2.2 億円）。1900 年・1901 年・2003 年など明らかな誤入力あり

### A-7. 顧客マスタの重複と欠損
- 同一「顧客名＋電話番号1」の重複疑い: 671 組・延べ 1,613 件
- 都道府県が空: 23,313 件（30.6%）
- Email 入力率: 3.8%（電話番号は 91.1%）

→ **メール施策を打つ土台がない。** 一方、営業管理側には 2026 年分だけで
　 メールアドレスが 8,731 件（29.0%）入っており、こちらのほうが新しい連絡先を持っている。

## B. すぐに着手できる打ち手

### B-1. 名寄せによる「見込み客 → 受注」の接続
営業管理と契約管理を顧客名＋企画名で突合し、営業管理側に顧客IDを遡及入力する。
既に顧客マスタ側に「営業管理レコードNo」ルックアップがあり、2024 年以降 510 件で使われ始めている
ので、この導線を正とするのが自然。

### B-2. 企画（プロジェクト）別の収益ダッシュボード
契約管理は 2010 年から途切れなく蓄積されており、データ品質が最も高い。
プロジェクト × 年 × 担当者の集計は現状のデータのままで信頼できる。
プロジェクトマスタの `受注目標`／`件数目標` を埋めれば、目標対比まで一気に出せる。

### B-3. リピート顧客の抽出
契約実績のある 3,914 名のうち 1,179 名が 2 本以上、65 名が 10 本以上契約している。
上位常連への企画別アプローチリストは、既存データだけで即座に作れる。

### B-4. 重複クレンジング
- 顧客マスタ: 「顧客名＋電話番号1」671 組の統合
- 営業管理: 「顧客名＋プロジェクトID」10,339 組の重複整理

### B-5. 請求・入金の再設計判断
2019 年以降のブランクを埋めるのか、契約管理までを kintone の責務と割り切るのかを決める。
割り切る場合は 95/96 をアーカイブし、契約管理に「入金済みフラグ」だけ残すのが現実的。
（契約管理の `入金状態` は 2024 年以降すべて「(内部データ)」で、実質機能していない）

## C. 技術的な注意点

- **jQuery 1.12.4 / jQuery UI 1.12.1** を CDN 参照している。JS カスタマイズは一覧の絞り込み補助のみで
  業務ロジックはないため、差し替え／撤去のリスクは低い。
- 8 アプリすべてで **プロセス管理は無効**。承認フローは kintone 上に存在しない。
- 営業管理(105) のような大規模アプリでは、`フィールド != ""` を条件にした `totalCount` が
  実測と一致しないことがある（`docs/03` 冒頭の注記を参照）。件数は `= ""` で取るか実データを数えること。
- offset は 10,000 が上限なので、全件取得は `$id > n order by $id asc limit 500` のカーソル方式を使う
  （`tools/kintone_client.py` の `fetch_all()` に実装済み）。
