## 2. データモデル（ID による疎結合）

kintone の関連レコード機能ではなく、**文字列の ID を各アプリにコピーして持たせる**設計。
参照整合性はアプリ側で保証されていないため、後述のとおり不整合が発生している。

```
プロジェクトマスタ(91)          担当者マスタ(90)         顧客マスタ(89)
  プロジェクトID  ───┐            担当者ID ───┐            顧客ID ───┬───┐
                     │                        │                       │   │
パッケージマスタ(92)  │                        │                       │   │
  パッケージID ──┐   │                        │                       │   │
                 │   │                        │                       │   │
                 ▼   ▼                        ▼                       ▼   │
             ┌──────────────────────────────────────────────────┐         │
             │ 契約管理(94)                                      │         │
             │   契約番号 = プロジェクトID-パッケージID-顧客ID     │         │
             └───────────────┬──────────────────────────────────┘         │
                             │ 契約番号                                    │
                 ┌───────────┴───────────┐                                 │
                 ▼                       ▼                                 │
          請求管理(95)             入金管理(96)                             │
          （2019年で停止）          （2019年で停止）                        │
                                                                           │
             ┌─────────────────────────────────────────────┐               │
             │ 営業管理(105)  顧客ID / プロジェクトID を保持 │───────────────┘
             └─────────────────────────────────────────────┘
                     ▲
                     └── 顧客マスタ(89) の「営業管理レコードNo」がここをルックアップ
                         （＝営業管理の見込み客を顧客マスタへ昇格させる導線）
```

### 契約番号の採番ルール
`契約番号` = `プロジェクトID` + `-` + `パッケージID` + `-` + `顧客ID`
（例: `172-MB07-372226` = プロジェクト 172 / パッケージ MB07 / 顧客 372226）

プロジェクトID は数字 3 桁のものと `B40` `B92` のような英数字のもの（書籍系）が混在する。

## 3. 業務フロー（データから読み取れる実態）

1. **見込み客の獲得** — 営業管理(105) に、SNS（Instagram が大半）や問い合わせ経由で見つけた
   作家を、企画（プロジェクト）ごとにリスト登録する。1 レコード＝1 営業対象。
2. **アプローチ** — 営業フェーズ（資料送付 → 提案 → 検討 → 最終調整 → 口頭契約 → 受注 / 失注 / 長期保留）
   を更新しながら追客する。連絡内容・メモは自由記述。
3. **受注** — 契約管理(94) にパッケージ単位で契約を登録。金額は `単価 × 数量 − 値引き`。
4. **顧客台帳化** — 契約に至った相手を顧客マスタ(89) に登録（新規登録は年 100〜300 件）。
5. **請求・入金** — 請求管理(95)／入金管理(96) は 2019 年で更新が止まっており、
   現在の請求・入金業務は kintone 外（会計ソフト等）で行われていると考えられる。

## 4. JavaScript カスタマイズ

8 アプリすべてが同じ構成の JS を読み込んでいる（すべて 2016-11-18 作成、作者は Kenji Akeno）。

| ファイル | 役割 |
| --- | --- |
| jquery 1.12.4 / jquery-ui 1.12.1（CDN） | 外部ライブラリ |
| `COMMON_01_Const.js` | アプリ ID の定数定義（89/90/91/92/105） |
| `COMMON_02_FormObject.js` | 一覧上の絞り込みテキストボックス（マスタ検索によるオートコンプリート） |
| `COMMON_03_List.js` | 一覧画面へ絞り込み UI を差し込む共通処理 |
| `Z01_eigyo.js` / `Z02_keiyaku.js` / `Z03_seikyu.js` / `Z05_kokyaku.js` 等 | アプリごとの絞り込み対象フィールド定義 |

**業務ロジックは一切なく、一覧画面の検索補助のみ。** 金額計算はすべて kintone の計算フィールド、
アプリ間のデータ連携は手作業またはルックアップに依存している。
なお jQuery 1.12.4 は 2016 年時点のバージョンで、10 年近く更新されていない。

## 5. プロセス管理（ワークフロー）

8 アプリすべてで **プロセス管理は無効**。承認フローは kintone 上に存在しない。
